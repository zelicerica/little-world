# Little World

A small village with six residents, private memories, limited resources, and optional hosted AI decisions. The concept and initial implementation were proposed and generated by ChatGPT/Codex, then developed collaboratively and tested locally.

Current version: **1.4.1**. Start offline, or use your own OpenAI API key through the local server. Each resident has a separate personality and context; all six share the configured model and request budget.

## Why this is worth building

Little World makes an usually invisible part of AI visible: what happens between receiving information, making a choice, and living with the result.

What I find interesting about this project is that a broken refrigerator can become a whole chain of decisions. Someone notices the failure. Someone else needs to hear about it. A mechanic needs parts, a clerk controls funding, and food keeps spoiling while the village responds. No single resident has the player's complete view. Even a sensible choice can arrive too late, or depend on a conversation that never happened.

That makes a small village a useful place to ask a bigger question: **how do separate decision-makers coordinate when their knowledge, priorities, and resources differ?** You can watch an answer unfold, inspect the evidence behind it, change a condition, and try again. The visual world gives those questions a story people can follow.

## What people can learn

- **The difference between information and understanding.** Seeing the whole map does not mean a resident knows everything on it. Follow a refrigerator warning from a direct observation into someone else's memory. Ask whether a poor decision came from missing information, outdated information, or the decision policy itself.
- **How cooperation depends on more than individual ability.** A capable mechanic still needs supplies and funding. A courier can help by carrying news rather than fixing anything personally. The village makes dependencies and coordination delays visible.
- **How small decisions produce larger patterns.** Buying a meal, protecting a food buffer, funding parts, or sharing with a neighbor changes what others can do next. Local priorities can help or hurt a shared outcome without anyone explicitly choosing that outcome.
- **What an LLM adds—and how to measure it.** Compare offline rules with occasional model-selected actions. A convincing explanation is something to examine alongside repair time, spoilage, hunger, and resource use. The current comparison measures a mixture of hosted choices and offline rules; repeated trials are needed before drawing broader conclusions.
- **Why AI needs boundaries outside its prompt.** The model proposes an action from a legal list. Code validates that choice and controls money, inventory, and movement. This is a concrete way to learn the difference between asking an agent to behave and limiting what it can actually do.
- **How to investigate a system.** Saved stories, recorded events, and replay let you trace what happened. The public explanation is a model's reported reason, not direct access to its internal reasoning. Compare that explanation with the resident's available information and the action's actual result.
- **How to build software responsibly.** A playful project still needs private credentials, validated imports, tests, bounded API use, clear documentation, and honest reporting of what has and has not been verified.

These lessons apply to thinking about workflows, organizations, and agent systems. Little World is a simplified teaching environment; its residents and outcomes do not establish how real people think or behave. A character's memories, personality label, or dialogue also does not demonstrate consciousness or human-like feelings.

## Why keep building?

The value of adding a feature is the question it lets someone investigate. Longer-term memory could let us test whether residents retrieve useful information or keep acting on stale reports. Different communication rules could reveal how news bottlenecks affect recovery. More scenarios and repeated comparisons could show whether an apparent improvement survives a change in starting conditions.

Those are possible directions, not features already implemented. Keeping the village small enough to inspect is part of its value: each addition should make an important behavior easier to observe and test.

A useful first experiment is to run the refrigerator crisis offline, inspect what Ben and Finn knew before repairs were funded, and then run the bounded hosted comparison. If the outcomes differ, trace the first meaningful difference in information or action. If they look similar, that is useful too: a more elaborate decision-maker does not automatically improve this particular task.

The reason to keep building is to turn curiosity about AI into experiments that people can understand, question, and reproduce.

## Choose how to play

| Mode | What to open | Installation | API charges |
| --- | --- | --- | --- |
| Offline | `Little_World.html` | None | None |
| Hosted AI | `Start_Little_World.cmd`, then the printed local URL | Node.js 22.9+; dependencies install on first run | Requests use your API account |

Download the repository with **Code → Download ZIP**, then **Extract All**. Run files from the extracted folder. Keep the whole project for hosted mode. A GitHub ZIP is the source download; there is no separate `Little_World.zip` required.

## Offline quick start

1. Double-click `Little_World.html` in the extracted folder.
2. Press **Play**, or **Step** to advance fifteen simulated minutes.
3. Click a resident to inspect their needs, goal, current choice, and memories.
4. Try **Storm & cold-store outage** to start the refrigerator crisis.

The standalone file uses offline rules, with no API key or network access required. Closing the tab loses unsaved progress. Use **Save world** before leaving.

## Hosted AI on Windows

1. Install Node.js **22.9 or newer** if needed. Close and reopen terminals after installation.
2. In the extracted project folder, copy `.env.example` to `.env.local`. In File Explorer, enable **View → Show → File name extensions** and make sure it is not named `.env.local.txt`.
3. Edit `.env.local` locally in a text editor. Set `OPENAI_API_KEY` to your own key and `LITTLE_WORLD_AI_ENABLED=true`. Keep the key private; never paste it into chat, browser controls, screenshots, or GitHub.
4. Double-click `Start_Little_World.cmd`. It installs dependencies if needed and starts the server. Keep this terminal open.
5. Open the URL printed by the server, normally **http://127.0.0.1:4173**. Hosted mode requires this local page; opening the standalone HTML does not enable it.
6. Enable **Let all six use hosted AI**, then press **Play** or **Step**. The journal records the resident, model, readable action, and short public explanation. Filter **Hosted AI & fallbacks** to follow model decisions.
7. Press **Pause** to stop new simulation steps. A request already in flight can finish and count toward usage. Close the terminal or press **Ctrl+C** to stop the server.

Equivalent commands from the extracted project folder:

```sh
npm ci
npm start
```

If `.env.local` is missing, the launcher creates it from the blank example. Edit it and restart the server to enable AI. Keep your existing key file when updating. Account access, permissions, and API funding must work independently; a ChatGPT subscription does not configure API billing.

### Configuration

| Setting in `.env.local` | Default | Meaning |
| --- | --- | --- |
| `OPENAI_API_KEY` | Blank | Loaded by the server only |
| `LITTLE_WORLD_AI_ENABLED` | `false` | Set to exactly `true` to make hosted mode available |
| `LITTLE_WORLD_MODEL` | `gpt-5.4-mini` | Model used by all six residents; your account must have access |
| `LITTLE_WORLD_MAX_REQUESTS` | `20` | Shared provider-attempt limit per server run; allowed range 1–100 |
| `LITTLE_WORLD_MAX_OUTPUT_TOKENS` | `256` | Output bound per request; allowed range 64–512 |
| `LITTLE_WORLD_TIMEOUT_MS` | `8000` | Provider deadline; allowed range 1000–15000 milliseconds |
| `PORT` | `4173` | Local port; allowed range 1024–65535 |

Restart the server after editing settings. The request counter resets on restart and is shared across tabs and comparisons. Failed provider attempts also consume the limit. These limits **do not impose a dollar spending cap**.

Residents rotate in cast order: Ada, Ben, Cleo, Dev, Emi, Finn. A busy resident keeps their turn until ready. There is at most one hosted opportunity every simulated hour across the village, and one active provider request at a time. Offline rules fill the turns between requests and handle invalid choices, outages, timeouts, or exhausted limits. You do not need to multiply the request limit by six.

## Controls and saved stories

| Control | What it does |
| --- | --- |
| Play / Pause | Starts or pauses the simulation |
| Step | Advances fifteen simulated minutes |
| Speed | Changes how quickly simulation steps are requested; hosted calls still take real time |
| Click a neighbor | Shows their possessions, needs, goal, memories, relationships, and latest explanation |
| Decisions | Includes routine action choices in the journal |
| Journal filters | Select a resident or event type, including the crisis and hosted fallbacks |
| Delay a shipment | Delays the next food delivery by eight simulated hours |
| Storm & cold-store outage | Pauses harvests and starts or extends a refrigerator crisis |
| Donation | Adds a recorded 100 coins to the town budget |
| Save world / Load | Downloads or restores a JSON story |
| Replay / slider / Return to live | Views recorded snapshots without calling a model |
| New day | Resets the entire village; save first to keep the current story |

Nothing is saved automatically. Existing schema-version-1 story saves remain compatible, subject to import safety limits. The interface stops long runs near 12,000 events. Imports are limited to 40 MB, 12,000 events, bounded memory text, and at most two million expanded compact-memory references. A modified or excessive save can be rejected. Save files contain simulation state and recorded model text, so review them before sharing.

## The refrigerator crisis

Click **Storm & cold-store outage**, then **Play**. The market alarm and workshop reveal the failure locally. Other residents must hear about it through conversations; knowing about rain does not grant knowledge of the broken refrigerator.

Ada warns neighbors, Dev carries news and reserve food, Ben requests funding and repairs the refrigerator, Finn funds parts while protecting a budget reserve, Emi cooperates after learning of the problem, and Cleo helps residents. Those are the offline priorities; hosted choices can differ.

Repairs need three funded refrigerator parts and three workshop supplies. Every simulated hour, up to two market meals spoil until repairs finish. The crisis panel shows the player's all-seeing view, including repair progress, spoiled meals, and who has heard the news. The residents' private memories remain separate from this player view. A low budget or poor decisions can delay recovery; a donation can help funding.

## Compare outcomes

**Compare two days** runs two offline 24-hour trials, one with an eight-hour shipment delay. Both start from the original snapshot. The shortage checkbox gives both trials low food. This comparison makes no API calls.

**Run crisis comparison (uses API)** explicitly authorizes hosted requests, even if the live hosted checkbox is off. Both trials start from the same original snapshot and random state, receive the same storm, and run for 24 simulated hours. One uses offline rules; the other rotates hosted opportunities with offline rules between them.

1. Choose a comparison maximum of **1–20** requests; default **12**. It is further bounded by the server's remaining shared allowance.
2. Click **Run crisis comparison (uses API)**. Your live village is unchanged. Requests may take a few minutes.
3. Read repair time, spoilage, combined hours hungry, successful gifts/conversations, remaining budget, and hosted opportunities/accepted choices. Opportunities can exceed accepted choices when requests fail or are declined.
4. Use **Save offline trial** or **Save hosted trial** to download a normal story. Load either file to inspect residents and replay its history. Replay makes no model calls; resuming live play with hosted mode enabled can make new calls.
5. **Save comparison report** downloads both trials and metrics together. It is a report, not a normal Load-world file.

**Cancel comparison** stops further requests and discards incomplete results. Requests already sent can still count and be billed. One trial shows what happened in that run; it does not establish that either policy is generally better.

## Update an existing installation

1. Stop the current server and save any story you want to keep.
2. Download and extract the latest full repository into a **new folder**.
3. Copy your existing private `.env.local` into the new folder on your computer. Do not upload it.
4. Run `Start_Little_World.cmd` in that new folder and refresh the local page. Keep the old folder until the update works.

If updating in place instead, preserve `.env.local`, run `npm ci`, and restart. The included `dist/` files and standalone HTML are built already. Source edits require `npm run build`.

## API key and sharing

The key is read from the server environment, held in the server process, and sent as an authorization header to **https://api.openai.com/v1** over HTTPS. The provider endpoint is pinned and redirects are rejected. The browser receives a temporary local session token, **not your OpenAI API key**. The server excludes environment files and server source from its static-file routes. Error responses omit raw provider errors.

`.env.local` is ignored by Git. The committed `.env.example` contains a blank key. Share the GitHub source download or standalone HTML, rather than zipping your working folder: a manual ZIP can include ignored private files. This review does not inspect the key file on your Windows computer. A compromised computer, privileged browser extension, or debugging tool can still access information available to that environment.

Source code can be shared publicly without embedding a user's key; each person configures their own key locally. The Node server is intended for **local use on 127.0.0.1**. Do not expose it through a tunnel or public hosting without a separate design for authentication and spending controls. See [SECURITY.md](SECURITY.md) for the review scope, fixes, and limitations.

## Architecture and development

- `src/engine.ts`: authoritative clock, resources, typed legal actions, offline policies, private observations, provenance, events, saves/replay, and comparisons.
- `src/hosted.ts`: bounded per-resident model context, canonical personalities, local observations, and legal action labels.
- `src/ui.ts`: map, inspector, journal, controls, opt-in, and downloads. Model/imported text is escaped before HTML rendering.
- `server/app.mjs`: loopback HTTP service, origin/Host/session checks, static-file allowlist, limits, and redacted errors.
- `server/provider.mjs`: stateless structured OpenAI Responses calls via the installed AI SDK; no model tools, shared conversation, retries, or previous-response ID.
- `scripts/build.mjs`: TypeScript output and self-contained HTML packaging.
- `scripts/check-secrets.mjs`: redacted credential-pattern scan of tracked files and reachable local Git blobs; requires Git.

The engine, rather than the model, owns money, food, inventory, movement, and action completion. The model selects an indexed legal action and supplies a short public explanation and optional decorative dialogue. Dialogue does not become factual evidence. Talk actions transmit only a known fact with its source preserved. Hosted requests use `store:false`; this setting alone is not a claim of zero provider retention. Do not put sensitive real-world information into imported village memories.
